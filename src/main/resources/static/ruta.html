CAP 1

🚀 El Despertar Reactivo

Fundamentos

La Analogía del Mesero 🍽️

Imagina un restaurante con un solo mesero (Event Loop).

Modelo Imperativo: El mesero toma tu pedido, va a la cocina y espera a que la comida esté lista. Nadie más es atendido.

Modelo Reactivo: El mesero toma tu pedido, lo deja en la cocina y vuelve inmediatamente a atender otra mesa. Cuando la cocina avisa, él entrega.

Imperativo vs Reactivo — hilo bloqueante vs event loop libre
EVENT LOOP

¿Qué es el Event Loop y cómo funciona?

El Event Loop es el corazón del modelo reactivo. Es un único hilo que:
1. Recibe eventos (requests, respuestas de DB, I/O)
2. Los encola en un Event Queue
3. Los procesa uno a uno, sin bloquearse nunca
4. Delega las operaciones lentas (I/O, red, DB) a workers y continúa

Flujo del Event Loop

El Event Loop procesa la cola sin bloquearse. Cada operación I/O se delega y el hilo queda libre.

Context Switch vs Event-Driven

Modelo imperativo: muchos hilos, muchos context-switches, CPU desperdiciada esperando. Reactivo: un hilo, cero bloqueos.

Pipeline Reactivo — datos fluyen a través de operadores

Flux.from(DB)
→
.filter(x > 0)
→
.map(x × 2)
→
.flatMap(save)
→
.subscribe()
El flujo de datos: Filtrado → Transformación → Entrega. Nótese que en reactivo el hilo nunca queda "durmiendo".
🛑

¡Alto ahí! El error más común en WebFlux

¿Qué pasa si usas .block() dentro de un controlador de WebFlux?

⚠️ ¡Catástrofe total!

Estás deteniendo el Event Loop. Como solo hay pocos hilos Netty (CPU × 2), si bloqueas uno, ¡toda la aplicación deja de responder a nuevos usuarios!

// ❌ NUNCA en WebFlux:
public String getDatos() { return service.getData().block(); }

// ✅ Devuelve el Mono/Flux directamente:
public Mono<String> getDatos() { return service.getData(); }
CAP 2

📚 El Glosario de Poder

Flux <T>

0 a N elementos. Como un río de datos. Emite con onNext, termina con onComplete o onError. 

Flux.just(1,2,3)
Mono <T>

0 ó 1 elemento. La promesa reactiva. Ideal para operaciones CRUD que devuelven un solo objeto.

Mono.just("hola")
Backpressure

El consumidor controla al productor: "Oye, envíame solo 10 elementos por ahora". Evita OOM.

Schedulers

Directores de orquesta. Deciden en qué pool de hilos se ejecuta cada tarea: boundedElastic(), parallel().

Cold Observable

Empieza desde el principio para cada suscriptor. Como Netflix: si llegas tarde, la película empieza desde el inicio.

Hot Observable

Emite datos siempre, independiente de suscriptores. Como la radio: llegas cuando llegas y escuchas lo actual.

subscribeOn()

Define el scheduler para el origen del flujo. Afecta todo hacia arriba. Úsalo con código bloqueante.

publishOn()

Cambia el scheduler para los operadores hacia abajo. Permite cambiar contexto a mitad del pipeline.

CAP 3

🏗️ La Tubería Mágica — Operadores

map()
Transformación síncrona 1:1. Nunca genera nuevos flujos. 
.map(user -> user.getName())
flatMap()
Tarea asíncrona: devuelve un Publisher. Sin orden garantizado, máxima concurrencia. 
.flatMap(id -> db.find(id))
concatMap()
Como flatMap pero mantiene el orden. Procesa uno a uno secuencialmente. 
.concatMap(id -> processOrdered(id))
switchMap()
Cancela el flujo anterior al llegar un nuevo elemento. Ideal para typeahead/búsqueda en vivo. 
.switchMap(q -> api.search(q))
filter()
Solo pasan elementos que cumplan el predicado. 
.filter(x -> x > 0)
take(n)
Solo los primeros N elementos, luego cancela. 
.take(10)
distinct()
Elimina duplicados. Cuidado con flujos infinitos (mantiene estado). 
.distinct()
debounce()
Espera X tiempo de silencio antes de emitir. Inputs de usuario. 
.debounce(Duration.ofMillis(300))
zip()
Combina N flujos en tuplas. Como una cremallera: espera uno de cada fuente. 
Mono.zip(getUserMono, getOrdersMono)
     .map(t -> buildDto(t.getT1(), t.getT2()))
merge()
Fusiona N flujos sin esperar orden. Emite según van llegando. 
Flux.merge(stream1, stream2)
combineLatest()
Combina el último valor de cada fuente cada vez que alguna emite. 
Flux.combineLatest(f1, f2, (a,b) -> a+b)
onErrorReturn()
Si hay error, devuelve un valor por defecto y el flujo completa normalmente. 
.onErrorReturn(User.defaultUser())
onErrorResume()
Si hay error, continúa con un flujo alternativo (caché, fallback). 
.onErrorResume(e -> cache.get(key))
retry(n)
Reinicia la suscripción N veces ante error. Errores transitorios de red. 
.retry(3).onErrorReturn(fallback)
doOnError()
Side-effect al error: logging, métricas. No modifica el flujo. 
.doOnError(e -> log.error("Error", e))

map()

Transforma el dato de forma síncrona. Como cambiar el color de una pelota.

.map(user -> user.getName())

flatMap()

Inicia una tarea asíncrona (DB, HTTP) y espera el resultado sin bloquear.

.flatMap(id -> db.find(id))
CAP 4

⚡ Rendimiento Real — ¿Por qué molestarse?

Simulación: 100 requests × 200ms latencia cada una 
// ❌ Imperativo — 1 hilo por request
// 100 × 200ms = 20 segundos en secuencia
// 100 hilos durmiendo consumiendo ~50MB RAM
for (String id : ids) {
    User user = userService.findById(id); // bloquea 200ms
    result.add(user);
}
🔴 Problema: Cada hilo queda dormido esperando. Bajo carga: thread pool agotado → OutOfMemoryError.
// ✅ Reactivo — 1-2 threads, 1000+ requests concurrentes
// 100 × 200ms ≈ 200ms totales (paralelo)
Flux.fromIterable(ids)
    .flatMap(id -> userService.findById(id))
    .collectList();
// El hilo queda libre durante el I/O
🟢 Ganancia: El mismo hilo atiende miles de usuarios. Throughput hasta 10× mayor con menos memoria.
CAP 5

✨ La Chispa de la Vida — .subscribe()

En WebFlux, un flujo es Lazy (perezoso). El código no se ejecuta hasta que alguien se suscribe.

Sin .subscribe() 🌑

Es como una manguera conectada al grifo, pero el grifo está cerrado. El agua no fluye.

Flux.just("Dato").map(v -> v.upper()); // nada
Con .subscribe() 🌟

Abrir el grifo. En ese momento los datos empiezan a viajar por la tubería.

flux.subscribe(v -> System.out.println(v));

💡 En Spring WebFlux, el framework hace el .subscribe() por ti cuando retornas un Mono o Flux desde un controller.

CAP 6

🌊 El Arte de No Ahogarse — Backpressure

¿Qué pasa si un servidor envía 1.000.000 registros/seg pero solo puedes procesar 100?

Backpressure es el mecanismo por el cual el consumidor controla la velocidad del productor, evitando desbordamiento de memoria.
Controlando la tasa
flux.limitRate(10) // pide de 10 en 10
    .subscribe(data -> process(data));
Estrategias de desborde
.onBackpressureBuffer(100) // buffer
.onBackpressureDrop()       // descarta
.onBackpressureLatest()     // solo último

ENTREVISTA

🎤 Preguntas de Entrevista Real

¿Cuál es la diferencia entre map() y flatMap() en Reactor?
map() transforma síncronamente. Es 1:1 — un elemento entra, un elemento sale. Devuelve el valor directamente.

flatMap() transforma asíncronamente. Cada elemento genera un Publisher (Mono/Flux) y los aplana. Ideal para llamadas a DB o HTTP anidadas. Sin orden garantizado.

Regla práctica: Si tu función devuelve un Mono/Flux → flatMap. Si devuelve un valor directo → map.
¿Por qué nunca deberías usar .block() en un controlador WebFlux?
WebFlux usa Netty con pocos hilos (CPU × 2). .block() duerme el hilo esperando. Si múltiples requests hacen esto, se agotan todos los hilos y la aplicación deja de responder. Anula completamente el beneficio del modelo reactivo.
¿Cuándo usarías subscribeOn() vs publishOn()?
subscribeOn(scheduler): define en qué scheduler se inicia el flujo. Afecta todo hacia arriba. Úsalo para código bloqueante en el origen (JDBC, leer archivos).

publishOn(scheduler): cambia el scheduler para los operadores hacia abajo. Permite cambiar de contexto a mitad del pipeline para tareas CPU-intensivas.
¿Qué es el backpressure y cómo lo maneja Reactor?
Mecanismo por el cual el consumidor controla la velocidad del productor. Reactor implementa el protocolo Reactive Streams: el suscriptor solicita explícitamente N elementos con subscription.request(n). Estrategias: limitRate(n), onBackpressureBuffer(), onBackpressureDrop(), onBackpressureLatest().
¿Cómo integrarías código bloqueante (JDBC) en una aplicación WebFlux?
Aislar el código bloqueante en Schedulers.boundedElastic():

Mono.fromCallable(() -> jdbcRepo.findById(id))
    .subscribeOn(Schedulers.boundedElastic())
La solución ideal es usar R2DBC (driver reactivo para SQL) para evitar el bloqueo por completo.
¿Cuál es la diferencia entre Cold y Hot Observable?
Cold (frío): Cada suscriptor recibe el flujo completo desde el inicio, como Netflix. Cada suscripción inicia una nueva ejecución.

Hot (caliente): Emite datos independientemente de suscriptores, como la radio. Si llegas tarde, solo oyes lo que hay ahora. Se crea con Sinks.many() o publish().
